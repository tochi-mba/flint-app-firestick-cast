# Slice 06 — second screen

**Governing ADR:** [ADR-0025](adrs/ADR-0025-SECOND-SCREEN-IS-APP-OWNED-PRESENTATION-CONTENT.md).

## Outcome

The television shows a Flint-owned surface — a player, a photo, what is playing now, a connection
dashboard — while the phone stays the cockpit. This is the mode Flint on Windows cannot ship, and the
first one that produces pixels.

## Entry criteria

- Slice 05 holds a session open.
- **The spike has passed on a real phone.** Nothing in the UI claims this mode before it has.

## The spike comes first, and it is throwaway

The whole design rests on one platform claim: a `VirtualDisplay` this app owns and renders into needs
no permission, because `VIRTUAL_DISPLAY_FLAG_PUBLIC` is what pulls in `CAPTURE_VIDEO_OUTPUT` and a
private display does not set it. That is what the documentation says. It is not necessarily what
every vendor's build does.

So the slice opens with a throwaway spike on real hardware: create the display, render one frame,
encode it. If an OEM restricts it, that is learned before anything is built on top rather than after.
The spike is then productised as the second-screen check in Settings, which creates a display only
this app can see, paints one frame a known colour and reads the pixel back. Checking the pixel rather
than merely that a frame arrived is the point: a display that produces correctly-shaped buffers full
of nothing is exactly the failure this project has already shipped once.

## User-visible vertical behaviour

1. Settings offers a second-screen check that says what it will do before it does it, and does not
   touch the television.
2. Until it has run, the mode reads Blocked with a remedy that runs it. If the phone refuses, the
   mode reads Not possible with no remedy, and mirror is unaffected.
3. Starting it shows a Flint surface on the television and a cockpit on the phone, with no permission
   dialog anywhere.
4. The card that offers it always says what it is not: the television shows Flint's own screens, not
   the phone's home screen and not other apps.

## Scope

### In scope

- The private `VirtualDisplay`, sized to the television's advertised dimensions.
- The `Presentation` host, and the Compose-in-Presentation wrapper.
- The encoder fed from the display's surface, and `SurfaceMode.PRESENTATION(4)` on the wire.
- A `surface-presentation` golden vector, generated by Rust and asserted by all three languages. The
  corpus has `surface-idle`, `surface-player` and `surface-browser` but not this one.

### Explicitly out of scope

- `MediaProjection`, consent, and foreground-service ordering. That is slice 07, and the separation is
  the reason this slice is first.
- Audio.

## The Compose-in-Presentation trap

A `Presentation` is a `Dialog`, so its decor view has no `ViewTreeLifecycleOwner`, no
`ViewTreeSavedStateRegistryOwner` and no `ViewTreeViewModelStoreOwner`. A `ComposeView` inside it
crashes until all three are set. This is wrapped once, in one place, rather than remembered at each
call site.

## Test-first implementation order

1. The spike, by hand, on a phone. Nothing else starts until it passes.
2. The golden vector, regenerated by Rust and asserted by C# and Kotlin, with the diff reviewed.
3. The Presentation wrapper, under Robolectric.
4. The encoder round trip, on the emulator.

## The test that matters most

A codec test that only checks structure is not a codec test. This project has already shipped an
encoder that produced correctly framed H.264 with correct parameter sets, correct dimensions and a
plausible bitrate, every frame of which decoded to nothing — flat green on the television, and
`ffprobe` read all 59 frames without complaint. Every structural assertion passed throughout.

So: render a known pattern into the display, encode it, decode the output with a second `MediaCodec`,
read the pixels, and assert the pattern survived. This cannot run as a JVM unit test or under
Robolectric — `MediaCodec` is real hardware and a real driver. It runs on the emulator nightly and on
a physical device before any release, and the default suite does not pretend to cover it.

## Full-suite checkpoint

The default suite, plus the emulator job.

## Exit evidence

- The spike, recorded, on a named phone.
- The encoder round trip green on the emulator, asserting pixels rather than structure.
- The `surface-presentation` vector byte-identical across Rust, C# and Kotlin.
- A copy test asserting the capability card never claims a desktop extension.

## Rollback and stop conditions

Stop, and say so, if the spike fails on a mainstream device: the mode is then Not possible on that
phone, which the verdicts already know how to report. Do not reach for
`VIRTUAL_DISPLAY_FLAG_PUBLIC` to work around it — that is a system permission, and asking for it
would make this a different product.
